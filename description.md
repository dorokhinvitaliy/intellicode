# IntelliCode Fabric — описание архитектуры

VS Code расширение: автономный AI-ассистент для работы с кодовой базой проекта.
Сочетает **RAG (Retrieval-Augmented Generation)** для семантического поиска по коду,
**локальные/облачные LLM** и **агентный цикл** для автономного выполнения задач
(создание/правка файлов, запуск команд).

Документ описывает, как устроены ключевые подсистемы, с акцентом на ML-часть:
эмбеддинги, векторное хранилище и гибридный поиск.

## 2. Векторные представления (эмбеддинги)

Эмбеддинг — это числовой вектор фиксированной размерности, который кодирует
семантику фрагмента кода. Близкие по смыслу фрагменты имеют близкие векторы.

### 2.1. Источники эмбеддингов

`LLMClient.createEmbedding()` поддерживает три пути:

1. **Ollama** (`/api/embeddings`) — локальная модель, напр. `nomic-embed-text`.
2. **OpenAI-совместимый эндпоинт** (`/embeddings`) — OpenAI, LM Studio с
   эмбеддинг-моделью (`text-embedding-3-small`, `qwen3-embedding` и т.п.).
3. **Локальный fallback** — собственная хэш-функция (см. ниже), если внешняя
   модель недоступна. Это гарантирует работу RAG без интернета и без отдельной
   эмбеддинг-модели.

Размерность вектора, полученного от сервера, **запоминается** и используется для
fallback, чтобы все векторы в хранилище были одной размерности (иначе косинус не
определён).

### 2.2. Локальный fallback-эмбеддинг (hashing trick)

Реализация в `LLMClient.createLocalEmbedding()` — это классический приём
**feature hashing** (hashing trick) поверх символьных n-грамм:

- Размерность вектора: **384**.
- Текст приводится к нижнему регистру, токенизируется.
- Для каждого токена извлекаются признаки:
  - **униграммы** (слова целиком), вес `1.0`;
  - **символьные биграммы** (окна из 2 символов), вес `0.5`;
  - **символьные триграммы** (окна из 3 символов), вес `0.3`.
- Каждый признак хэшируется функцией **djb2** в индекс `[0, 384)`, и его вес
  добавляется в соответствующую координату вектора.
- Итоговый вектор **L2-нормируется** (`v / ‖v‖`), чтобы скалярное произведение
  было эквивалентно косинусной близости.

Символьные n-граммы дают устойчивость к опечаткам и общим корням слов
(`useState`/`useEffect` попадут в пересекающиеся бакеты). Это не нейросетевой
эмбеддинг, но он стабилен, детерминирован и даёт рабочий семантический сигнал
поверх ключевых слов.

## 3. Индексация проекта (ProjectIndexer)

Превращает исходный код в набор проиндексированных чанков с векторами.

### 3.1. Обход файлов

- Рекурсивный обход рабочей папки.
- Игнорируются служебные директории (`node_modules`, `.git`, `dist`, `build`,
  `__pycache__`, `venv`, `target`, ...) и лок-файлы.
- Индексируются только поддерживаемые расширения (`.ts/.tsx/.js/.jsx/.py/.java/
  .go/.rs/.cpp/.cs/.rb/.php/.vue/.html/.css/.sql/.md/.json/...`).
- Пропускаются минифицированные и слишком большие файлы (> 100 КБ).

### 3.2. Чанкинг (разбиение на фрагменты)

Документ-уровень для RAG — это не файл целиком, а **семантический фрагмент**:

1. **Семантический чанкинг** (приоритетный): по регулярным выражениям выделяются
   границы функций, классов, интерфейсов, типов, методов (для JS/TS и Python).
   Каждый такой блок — отдельный чанк с метаданными (`symbolName`, `type`).
2. **Оконный чанкинг** (fallback): если семантику выделить не удалось — скользящее
   окно по строкам (`chunkSize` ≈ 60 строк, перекрытие `chunkOverlap` ≈ 10),
   чтобы не терять контекст на границах.
3. **Обзорный чанк файла**: отдельный чанк со списком `import`/`export` —
   помогает находить файлы по их зависимостям и роли в проекте.

### 3.3. Создание векторов и кэширование

- Эмбеддинги создаются **батчами** (по 20 чанков).
- **Инкрементальность**: для каждого файла хранится `mtime`; неизменённые файлы
  переиндексировать не нужно.
- **Очистка устаревшего**: чанки удалённых файлов вычищаются из хранилища.

Текст, который векторизуется, обогащается метаданными:
```
File: <имя>
Symbol: <имя символа>
Type: <function|class|module|...>
Language: <язык>
<содержимое чанка>
```
Это поднимает качество поиска: имя файла/символа попадает в эмбеддинг.

## 4. Векторное хранилище (VectorStore)

### 4.1. Хранение

- В памяти — `Map<id, CodeChunk>`, где чанк содержит код, метаданные и вектор.
- На диске — JSON-файл на каждый workspace (`vector_store_<hash>.json`),
  загружается при старте. Простое, прозрачное, легко инспектировать.

### 4.2. Метрика близости — косинусное сходство

```
cos(a, b) = (a · b) / (‖a‖ · ‖b‖)
```
При несовпадении размерностей возвращается 0 (защита от смешения разных
эмбеддинг-моделей).

### 4.3. Гибридный поиск (ключевая часть)

Чистый векторный поиск на коде слаб (имена переменных, точные совпадения важны),
поэтому используется **гибридное ранжирование** (`hybridSearch`) — линейная
комбинация нескольких сигналов:

```
score = 0.50 · vectorScore     (косинусная близость эмбеддингов)
      + 0.25 · keywordScore    (доля совпавших токенов запроса в чанке)
      + 0.10 · symbolScore     (запрос содержит имя символа)
      + 0.15 · pathScore        (запрос содержит части пути/имени файла)
```

Поверх базового скора применяются эвристические **бусты**:

- **+5.0** — если в запросе явно упомянуто имя файла (гарантирует, что нужный
  файл окажется наверху);
- **+0.15** — важные файлы (`package.json`, `README`, конфиги, `docker-compose`);
- **+0.10** — service-aware буст: запрос про фронтенд/бэкенд → приоритет
  соответствующим директориям (`/front`, `/client`, `/api`, `/server`).

После ранжирования — **фильтрация для разнообразия и бюджет контекста**:
- не более **2 чанков на файл** (чтобы выдача не забилась одним файлом);
- суммарный бюджет контекста ≈ **12 000 символов**.

Гибридный подход = recall векторного поиска + точность лексического (BM25-подобного)
поиска. Это стандартная индустриальная практика для RAG по коду.

## 5. RAG-конвейер (ChatHandler)

Полный путь от запроса пользователя к ответу LLM:

```
запрос
  │
  ├─ 1. Расширение запроса (query expansion)
  │      по интенту добавляются синонимы/связанные термины
  │      («запусти» → «start dev serve package.json scripts» и т.п.)
  │
  ├─ 2. Эмбеддинг каждого расширенного запроса (параллельно)
  │
  ├─ 3. hybridSearch по каждому → объединение по максимуму score → top-K
  │
  ├─ 4. Фильтрация (существование файла на диске, отсев node_modules/dist/...)
  │
  ├─ 5. Сборка контекста с лимитами (фрагменты обрезаются, общий бюджет ограничен)
  │
  └─ 6. Промпт: системный + история + (контекст кода) → LLM (стриминг)
```

**Расширение запроса** (query expansion) повышает recall: один запрос
пользователя превращается в несколько поисковых, покрывающих разные формулировки
(intent-based: запуск, ошибки, БД, API, UI). Если проект не проиндексирован —
этап поиска пропускается (оптимизация задержки).

## 6. Интеграция с LLM (LLMClient)

Универсальный клиент, провайдер выбирается настройкой `apiProvider`:

| Провайдер | Эндпоинт | Примечание |
|---|---|---|
| `ollama` | `http://localhost:11434` | локально, без ключа |
| `openai` | `https://api.openai.com/v1` | требует ключ |
| `anthropic` | `https://api.anthropic.com` | формат сообщений Claude |
| `custom` | произвольный | **LM Studio** (`http://localhost:1234/v1`) и др. |

- Чат — **стриминг** через SSE (`/chat/completions`, `stream: true`).
- Для reasoning-моделей (**qwen3**) есть переключатель «размышлений»: при выключении
  в промпт добавляется `/no_think`, блоки `<think>…</think>` вырезаются из вывода и
  из истории.

В проекте использовалась локальная модель **Qwen3-14B (MLX)** через **LM Studio**
(OpenAI-совместимый API), что делает решение полностью локальным и приватным.

## 7. Агентный режим

Командные запросы (создай / исправь / покрой тестами) выполняются как **автономный
агентный цикл** (вопросы — обычный одношаговый ответ).

### 7.1. Цикл

```
1. Собрать RAG-контекст по задаче
2. Сгенерировать шаг (LLM) → распарсить «инструменты» (маркеры)
3. Выполнить действия → собрать результаты ([OBSERVATIONS])
4. Вернуть результаты модели → перейти к шагу 2
5. Повторять, пока модель не выдаст <<<DONE>>>
```

### 7.2. Инструменты агента (текстовые маркеры)

| Маркер | Действие |
|---|---|
| `<<<READ_FILE path="..."/>>>` | прочитать файл |
| `<<<LIST_DIR path="..."/>>>` | перечислить файлы (для задач «по всем …») |
| `<<<CREATE_FILE>>>…<<<END_FILE>>>` | создать файл |
| `<<<EDIT_FILE>>>…<<<END_FILE>>>` | полная перезапись |
| `<<<APPLY_PATCH>>>` + `SEARCH/REPLACE` | **точечная правка** без перезаписи |
| `<<<EXECUTE command="..."/>>>` | выполнить команду (тесты, линт, сборка) |
| `<<<DONE>>>` | сигнал завершения задачи |

`APPLY_PATCH` использует **толерантное сопоставление**: точное совпадение, а при
неудаче — построчное сравнение без учёта отступов/пробелов (как в Aider/Cline),
т.к. небольшие модели не воспроизводят текст байт-в-байт.

### 7.3. Защита от зацикливания

Несколько механизмов не дают агенту «крутиться впустую»:

- **Закреплённый лог «уже сделано»** — список выполненных действий подмешивается в
  задачу каждый ход (не обрезается историей), чтобы агент не начинал задачу заново.
- **Детекция отсутствия прогресса** — если шаг повторяет те же действия (чтение,
  команда) без изменений в коде, агент получает подсказку «делай правки» и
  останавливается при повторе.
- **Падение тестов/линта = фидбэк, а не ошибка** — агент анализирует вывод и чинит,
  итерируя, пока множество ошибок меняется (есть прогресс).
- **Жёсткие лимиты-страховки** — потолок по числу шагов/операций и кнопка «Стоп».

## 8. Используемые ML/IR-концепции (резюме для защиты)

| Концепция | Где применяется |
|---|---|
| **Векторные эмбеддинги** | представление чанков кода числовыми векторами |
| **Feature hashing (hashing trick)** | локальный fallback-эмбеддинг |
| **Символьные n-граммы** | признаки для локального эмбеддинга |
| **L2-нормализация** | приведение векторов к единичной норме |
| **Косинусное сходство** | метрика близости в семантическом поиске |
| **RAG** | пополнение промпта релевантным кодом из проекта |
| **Гибридный поиск (dense + sparse)** | вектор + ключевые слова + символы + путь |
| **Query expansion** | повышение полноты выдачи |
| **Чанкинг (semantic chunking)** | разбиение кода на смысловые фрагменты |
| **MMR-подобная диверсификация** | лимит чанков на файл + бюджет контекста |
| **Agentic loop / tool use** | автономное выполнение задач LLM-агентом |

## 10. Краткий вывод

Расширение реализует полный **RAG-конвейер по кодовой базе**: индексация →
семантический чанкинг → векторизация → гибридный поиск → пополнение контекста LLM,
а поверх этого — **автономный агент** с инструментами и защитой от зацикливания.
Решение провайдер-агностично и может работать **полностью локально** (LM Studio +
Qwen3-14B + локальные эмбеддинги), что важно для приватности и автономности.
